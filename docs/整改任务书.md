## 0. 目标

在继续模拟盘长期运行前，消除四类结构性问题：

1. 单笔最坏亏损过大（现约权益 15%），仓位与风险脱钩。
2. 护栏在数据异常时放行、存在绕过路径。
3. 学习闭环在小样本上拟合噪声，且方向性偏向“越学越激进”。
4. 常驻进程与每日任务无人守护、无告警。
5. 本地订单状态、风险视图与交易所真实状态可能不一致（触发 ≠ 成交）。

不追求增加功能。每项改动以“更保守、更可审计”为准。

## 3. 阶段 P0：风控与执行（R1–R12、D1，必须先做完）

### R1 仓位改为按风险定额

**现状**：`size(保证金%) = 20 × min(1, |S|/0.6)`，|S|<0.3 再减半；杠杆由交易经理给（1–5）。单笔最坏亏损 ≈ 20%×5×15% = 权益 15%。

**改为**：新增纯函数模块 `desk/sizing.py`，所有开仓路径（`open_now`、`place_trigger`、限价补单）与日报统一调用它，不得各自计算。覆盖范围包括 `rediscuss`、`scripts/rerun_coin.py`，以及 `scripts/` 下会下单的运维脚本（`btc_demo_execute.py`、`eth_demo_backfill.py` 硬编码 13.156%、`reprice_triggers_limit.py`）：这些脚本要么改为调用 `sizing` + `check_open`，要么移入 `scripts/retired/` 并在运行时直接拒绝执行。任何建议仓位（含交易经理）都只能作为 sizing 的输入上限，不能绕过它。

```
scale      = min(1, |S| / full_size_consensus) × (0.5 if |S| < half_size_below else 1)
dd_scale   = clip(1 − drawdown / max_drawdown_pct, 0.25, 1)                 # 回撤越深风险越小；drawdown 见 R5
risk_usd   = equity_live × risk_per_trade_pct × scale × dd_scale × tm_risk_scale   # tm_risk_scale 见 L5，默认 1，只降不升
stop_dist  = |entry − stop| / entry + cost_buffer_pct                       # stop 由 R2 规则给出；cost_buffer 覆盖双边手续费与滑点
notional   = min(risk_usd / stop_dist,
                 equity_live × max_notional_per_trade_pct,
                 R4 给出的剩余额度)
leverage   = 满足 notional/leverage ≤ equity_live × max_margin_pct 的最小值，步长 0.5，下限 1，上限 swap.leverage_max
             再受交易经理 leverage 上限约束（只降不升）；若因此保证金超限，则按保证金上限反推削减 notional
```

- `notional < min_order_usd` 或张数 < minSz → 不下单，事件 `size_too_small`。
- `manager.aggregate` 只输出方向、入场、止损、止盈、周期、|S|；不再输出 `size_pct`。日报“计划保证金 x%”改为显示 risk_usd、notional、leverage、止损触发亏损额。
- 交易经理不再决定杠杆（见 L5）。

**新增配置**：

```yaml
risk:
  risk_per_trade_pct: 0.0075      # 单笔止损亏损占当前权益
  max_notional_per_trade_pct: 1.0 # 单笔名义上限（×权益）
  max_margin_pct: 0.20            # 单笔保证金上限（沿用原 20%）
  stop_atr_mult: 1.5              # R2
  stop_min_pct: 0.01              # R2
  stop_max_pct: 0.08              # R2（原护栏 15% 保留为最终兜底）
  tp_r_multiple: 2.0              # R2
  liq_buffer_atr_mult: 1.0        # R3
  max_open_risk_pct: 0.02         # R4
  max_net_directional_pct: 1.2    # R4
  max_daily_loss_pct: 0.025       # R5（取代原 5%）
  max_drawdown_pct: 0.10          # R5
  stop_cooldown_hours: 24         # L6
  cost_buffer_pct: 0.002          # R1，双边手续费 0.1%×2 的近似，实测滑点后可调
  max_price_drift_atr: 0.5        # D1
  require_full_stop_coverage: true # R11
```

**验收用例**（equity_live=100000，`full_size_consensus=0.6`、`half_size_below=0.3`，tm_risk_scale=1，无回撤，无其他持仓；下表按 `cost_buffer_pct=0` 计算以便核对，另测 cost_buffer=0.2%、止损 5% → notional=750/0.052≈14423.08；回撤 5%（max 10%）→ dd_scale=0.5，risk_usd 减半）：

| |S| | stop_dist | scale | risk_usd | notional | leverage | 保证金 | 止损亏损 |
|---|---|---|---|---|---|---|---|
| 0.60 | 5% | 1.0 | 750 | 15000 | 1 | 15000 | 750 |
| 0.60 | 2% | 1.0 | 750 | 37500 | 2 | 18750 | 750 |
| 0.60 | 1% | 1.0 | 750 | 75000 | 4 | 18750 | 750 |
| 0.45 | 3% | 0.75 | 562.5 | 18750 | 1 | 18750 | 562.5 |
| 0.20 | 5% | 0.1667 | 125 | 2500 | 1 | 2500 | 125 |

另测：交易经理给 leverage=2 而上表第 3 行需要 4 倍 → notional 被削到 40000（保证金 20000）。任何输入组合下“止损亏损 ≤ risk_usd + 1e-6”必须成立（属性测试）。

### R2 止损/止盈改为确定性规则

**现状**：止损、止盈、入场分别对同向角色加权平均，可能得出谁都没建议过的组合，且不检查盈亏比。

**改为**：

- 止损距离 = `clip(stop_atr_mult × ATR14 / entry, stop_min_pct, stop_max_pct)`，ATR14 取 `market_ctx` 中已收盘日线。
- 止盈 = 入场 ± `tp_r_multiple` × 止损距离。
- **入场改为“选方案”而不是“平均价格”**：同向角色按入场条件分为三组：`now`、`breakout`（做多涨到/做空跌到，触发价在现价之外的顺势方向）、`pullback`（逆势方向回调）。按组内 `Σ w×conf` 选出一组，入场价只在该组内加权平均。禁止跨组平均（例：A 涨到 110 买、B 跌到 90 买，绝不能平均成现价 100 立即买）。两组得分差 < 20% 时视为方案冲突，不开仓，事件 `plan_conflict`。
- 止损锚点与入场一致：用选中方案的入场价套 ATR 规则；周期取该组加权周期。日报写明选中哪一组、其他组得分。
- 角色给出的止损/目标只写入日报“角色参考”列，不参与执行。
- 原护栏“止损距离 ≤ 15%”保留为兜底。

**验收**：entry=100、ATR14=4 → 做多止损 94、止盈 112；做空止损 106、止盈 88。ATR14=0.3 → 止损距离被抬到 1%。现价 100，A（w=1,conf=0.8）breakout 110、B（w=1,conf=0.7）pullback 90 → 得分差约 13% < 20%，不开仓；B 改为 conf=0.3 → 选 breakout 组，入场 110，绝不出现入场 100。

### R3 止损与强平价之间留出缓冲

**现状**：只要求止损先于强平；强平价按维持保证金 0.5% 近似。

**改为**：要求 `|强平价 − 止损| ≥ liq_buffer_atr_mult × ATR14`，不满足则杠杆每次降 0.5 直至满足；1 倍仍不满足则拒绝（事件 `liq_buffer_reject`）。维持保证金率优先读 OKX `public/position-tiers`（缓存 1 天），读取失败才用 0.5% 近似，并在日报注明。

**验收**（用 0.5% 维持保证金近似）：entry=100、ATR14=12、做多止损 92（已被 stop_max_pct 夹到 8%）、初始 5 倍 → 强平 80.5，缓冲 11.5 < 12，降到 4.5 倍 → 强平约 78.28，缓冲约 13.7 ≥ 12，通过。另测 ATR14=4 时 5 倍直接通过、杠杆不变。

### R4 组合层敞口

**现状**：三币分别计算；总名义 ≤ 180%；权益基准固定为初始权益 101898.76。

**改为**：

1. `execution.equity_basis` 改为 `live`：所有风控与仓位计算用实时总权益（含浮盈亏）。读取失败 → 拒绝开仓（不回退初始权益）。日报同时显示初始与实时。
2. **同向净名义**：BTC/ETH/SOL 视为同一风险因子。`Σ(多头名义) − Σ(空头名义)`（含未触发条件单，按触发价）的绝对值 ≤ `max_net_directional_pct × 权益`。
3. **在途风险**：Σ(各持仓与条件单的 名义 × 止损距离) ≤ `max_open_risk_pct × 权益`。没有止损的持仓按 `stop_max_pct` 计。
4. 原总名义 180% 保留为最终兜底。
5. 超限时**先削减到剩余额度**，削减后低于最小下单再拒绝；事件 `size_clipped`（记录原值、削减后值、触发的限额）。

**验收**：已有 ETH 空 60000 名义 + SOL 空 50000 名义时，新开 BTC 空单的名义上限 = 120000 − 110000 = 10000；新开 BTC 多单不受净名义限制，但受在途风险限制。

### R5 当日亏损与回撤护栏：计入浮亏，出错拒绝

**现状**：只算 `positions-history` 首页已实现盈亏；接口失败按 0；按初始权益 5%。

**改为**：

- 新增 `state/equity_marks.json`：`day_start_equity`（北京时间每日首次读取时记录）、`peak_equity`（历史最高实时权益）。
- 当日亏损 = 实时总权益 − day_start_equity。≤ −`max_daily_loss_pct × day_start_equity` → 禁止开新仓，按 R10 撤销所有条件单与未成交入场子单（含受保护单），webhook `daily_loss_halt`。次日自动解除。
- 回撤 = 1 − 实时总权益 / peak_equity。≥ `max_drawdown_pct` → 自动写 KILL 文件（R7 路径），webhook `drawdown_kill`。只能人工删除 KILL 解除。
- 任一所需数据（balance、positions、equity_marks）读取失败 → 拒绝开仓，事件 `guard_data_unavailable`。
- `positions-history` 若分页（见 V6），日报统计已实现盈亏时必须翻页取全。

**验收**：模拟“已实现 0、浮亏 −3000、day_start=100000”→ 拒绝开仓；模拟 balance 接口抛异常 → 拒绝开仓；模拟 peak=110000、实时=98000 → 写 KILL。

### R6 限价补单走完整护栏

**现状**：`entry_limit._step` 市价补单前的 `_guard` 只查 KILL 与当日亏损。

**改为**：补单前调用与 `check_open` 同一套检查（含 R4、R5），视角为“原条件单已占用额度减去已成交部分”。补单张数只能 ≤ 原剩余张数，并按 R1/R4 剩余额度再削减。被拦截时只保护已成交部分，事件 `fallback_blocked`。

**验收**：模拟“补单时总在途风险已满”→ 不补单、已成交部分挂上止损。

### R6b 限价超时由事件驱动，而不是靠 5 分钟轮询

**现状**：`timeout_minutes=3` 只是判定阈值，不是处理时限。实际检查依赖 demo_watch 每轮（本轮耗时最长 150 秒 + 休眠 300 秒）。最坏情况：某轮在触发后 2 分 59 秒检查（未超时），本轮跑满 150 秒再休眠 300 秒，下一轮约在触发后 **10.5 分钟**才处理；若该轮拿不到 entry_limit 锁跳过，再加约 7.5 分钟。汇报中写明改造前后的实测最坏延迟。

**改为**：demo_ws 收到 `trigger_fired` 后在进程内起定时器，到点调用 `entry_limit._step`（持现有文件锁，与 demo_watch 互斥）；demo_watch 轮询保留为兜底。撤子单后必须查询该子单终态与实际成交量，再计算剩余张数（处理撤单与成交的竞态）。

**验收**：打桩 ws 触发事件，断言 3 分钟±10 秒内进入 cancelling；模拟“撤单返回成功但子单已全部成交”→ 不补单。

### R7 KILL / HALT 统一与语义明确

**现状**：配置注释写 `state/KILL`，代码读 `state/ledger/KILL`；KILL 时 `run_daily` 仍调用全部 LLM（`run_daily.py` 第 84 行 `st_note` 未使用）。

**改为**：

- 单一常量 `settings.KILL_PATH = state/KILL`，所有地方引用它。过渡期内旧路径 `state/ledger/KILL` 存在也视为生效，并在日志提示迁移。
- **KILL（停开仓）**：禁止 `open_now`、`place_trigger`、限价补单；按 R10 在 30 秒内撤销所有条件单与未成交入场子单（含受保护单）；**允许**平仓、减仓、收紧止损、持有期到期平仓。`run_daily` 在 KILL 下跳过全部 LLM 调用，只做盯市、复盘数据收集与日报，日报顶部标红“KILL 生效”。
- **HALT（全冻结）**：新增 `state/HALT`。除读取、通知外，禁止一切自动写操作（含到期平仓、改止损、补单）。交易所端已挂的止损止盈不动。
- **明确不做**：不要让 KILL 禁止平仓/减仓/收紧止损。
- 修正 `config.yaml` 注释、README、`scripts/rerun_coin.py` 中的路径；删除或启用 `st_note`。

**验收**：分别放 KILL、HALT，跑 `--mock` 日流程和一次 demo_watch（打桩 OKX），断言各写操作是否被调用符合上述语义。

### R8 每币执行锁

**现状**：`run_daily`、`rediscuss`、`rerun_coin`、`demo_watch` 可能同时对同一币写；“每币一仓”是先查后下，存在竞态。

**改为**：`state/locks/exec-<COIN>.lock` 阻塞 flock，超时 120 秒则放弃并记 `exec_lock_timeout`。锁的范围：从读取 `demo_exec.book` 到下单/平仓/改止损完成。**LLM 分析放在锁外**，拿到锁后重新读持仓与挂单再执行。

**验收**：两个进程同时对同一币调用开仓，只有一个成功，另一个看到已有持仓后拒绝。

### R9 交易经理缺席时撤单

**现状**：交易经理 LLM 异常 → 不开仓，但**不撤**旧条件单，旧单可能在过期判断下触发。

**改为**：缺席与否决一致，撤该币未受保护的条件单，原因 `tm_absent`。

### R10 已挂条件单随风险状态变化即时撤销或复核（重点核实项）

**问题**：OKX 条件单由交易所自行触发。`check_open` 只在挂单时运行，触发时账户状态（权益、其他持仓、KILL、日亏）可能已经变化。禁止新提交订单 ≠ 阻止已挂订单继续增加风险。

**改为**：

1. 以下事件发生后**立即**（不等下一轮轮询）对所有挂着的条件单重跑 R1/R4/R5 检查：KILL/HALT 出现、`daily_loss_halt`、`drawdown_kill`、任一开仓/平仓成交、权益较上次复核变化 > 2%。实现：demo_ws 进程内事件触发 + demo_watch 每轮兜底；KILL/HALT 文件由 demo_ws 每 30 秒检查一次。
2. 复核不通过 → 撤单（事件 `trigger_revoked`，带原因）。KILL、日亏、回撤触发的撤单**包括受保护的条件单**（`protected_algo_ids` 只防止被日常新决策替换，不防止紧急停机）。
3. 兜底：条件单成交后若组合超出 R4 限额（复核来不及时），立即对该新仓 reduceOnly 减到限额内，事件 `post_fill_reduce`，并发 webhook。
4. 先读代码核实现状并在 V 阶段汇报：目前 KILL 出现后，已挂条件单是否会被撤、多久会被撤。

**验收**：挂一张条件单后放 KILL → 30 秒内被撤；挂单后模拟日亏触发 → 被撤；受保护单在 KILL 下也被撤；模拟“成交后净名义超限 20%”→ 自动减仓。

### R11 幂等、崩溃恢复、对账与止损覆盖

1. **幂等**：所有会改变仓位的请求（市价单、条件单、平仓、减仓、改止损、重挂止损）都带确定性 `clOrdId`/`algoClOrdId`（由 decision_id + 动作 + 序号生成）。请求超时或异常时，先按该 ID 查询交易所，确认不存在再重试；绝不盲目重发。
2. **先登记意图再下单**：下单前先写本地 `intent`（含 clOrdId），成功后更新状态。进程重启时扫描未完成的 intent，按 clOrdId 去交易所查询并补齐登记。
3. **每轮对账**（demo_watch）：交易所持仓、算法单、普通挂单 vs 本地登记（含 R12 状态机）。交易所有、本地无 → 补登记（deadline 用默认周期）并告警 `orphan_position`；本地有、交易所无 → 先按 R12 查询订单终态再转入对应终态，不直接删除。
4. **止损覆盖不变量**（`require_full_stop_coverage`）：每个持仓必须有 reduceOnly 止损单，且张数 ≥ 持仓张数。不满足 → 立即按 R2 规则重挂（先挂新再撤旧），失败则 webhook `stop_coverage_missing`。部分成交、减仓、补单后都要立即检查一次。
5. 撤单返回成功后，查询订单终态确认未与成交竞态。

**验收**：模拟“下单请求超时但交易所已接受”→ 不产生第二笔；模拟“下单成功后、写登记前进程被 kill”→ 重启后自动关联；人为撤掉某持仓的止损单 → 下一轮被重挂并告警。

### R12 条件单生命周期：区分“触发”与“成交”

**问题**：文档 §5.1 写算法单 `state=effective` → 登记 positions → 事件 `trigger_filled` → 从 triggers 删除。但触发后提交的是限价子单（§3.11），可能长时间未成交、部分成交或被撤。`effective` 只说明触发生效，不等于已成交。可能影响：日报“已成交”不准；持有期从触发而非成交起算；子单待成交期间，护栏若只读 positions 与 orders-algo-pending，**看不到这笔在途风险**，同币可能被再次开仓；登记表提前清理会丢失订单关联。

**改为**：

1. 每笔入场一个统一状态机，存 `state/ledger/entries.json`（可与 `entry_limit.json` 合并，以一个为准，另一个迁移后废弃）：

| 状态 | 含义 | 风险额度 | 允许的操作 |
|---|---|---|---|
| `armed` | 条件单已挂，未触发 | 按触发价 × 张数计入 | 撤单、R10 复核 |
| `triggered` | 算法单 effective，子单 ordId 未确认 | 按全部张数计入 | 查询子单；禁止同币新入场 |
| `working` | 子单挂着，0 成交 | 按全部张数计入 | 超时撤单（R6b）；禁止同币新入场 |
| `partial` | 部分成交 | 已成交部分按持仓计，剩余按挂单计 | 撤剩余、补单（R6）、已成交部分必须有止损（R11.4） |
| `filled` | 全部成交 | 按持仓计 | 转入 positions，开始计 deadline |
| `canceled` / `expired` | 终态，可能带部分成交 | 已成交部分按持仓计 | 只做保护与登记 |

2. 事件改名：`trigger_fired`（触发）与 `entry_filled`（以子单实际成交确认，带成交量与均价）分开。不再用 `trigger_filled` 表示触发。日报“已成交”只统计 `entry_filled`。
3. **deadline 从首笔实际成交时间起算**，不是触发时间。
4. 护栏视图（`demo_exec.book`）必须加入普通挂单 `/trade/orders-pending`：未成交子单的名义与止损风险计入 R4；该币存在 `triggered/working/partial` 时视同已有持仓，拒绝同币新入场。
5. 登记表只在终态清理，删除“开仓登记超过 10 分钟即删除”这类按时间的经验规则。
6. R10 的紧急撤单范围包括 `working/partial` 子单，同时阻止补单。

**验收**：打桩“算法单 effective、子单 0 成交” → 状态 `working`，日报不显示已成交，deadline 未开始，护栏计入其名义，同币新入场被拒；打桩“部分成交 40% 后超时、补单被 R10 拦截” → `partial → canceled`，止损覆盖已成交的 40%，deadline 从首笔成交起算。

### D1 数据新鲜度与执行前复核

1. **OKX 日线失败不得回退 Yahoo 用于交易**：Yahoo 是现货/指数口径，与 OKX 永续不同。回退数据只允许用于报告，该币当日禁止开新仓（`data_fallback_no_trade`）。
2. 每份输入（日线、资金流、宏观、x_feed）记录 `source`、`data_time`、`ttl`。决定开仓所需的日线与最新价超出 ttl → 禁止开仓；其他输入过期按 L4 处理。
3. **执行前复核**：从分析开始到执行之间价格可能已变化。执行前重新读最新价与账户；`|最新价 − 分析时价格| > max_price_drift_atr × ATR14` → 不执行，事件 `price_drift_skip`，交给下一次决策。
4. **配置安全校验**：启动时校验所有安全相关配置项是否有代码读取。存在但未被执行的安全项（如 `guardrails.leverage`、`allow_leverage`）→ **启动失败并报错**，而不是静默忽略。`guardrails.leverage: 1` / `allow_leverage: false` 与实际生效的 `swap.leverage_max: 5` 互相冲突，**不得通过删除前两项来消除冲突**，按 Q11 处理。

**验收**：打桩 OKX 日线失败 → 当日该币不开仓；最新价偏离 0.6×ATR → 跳过；config 里保留 `allow_leverage: false` 而无代码读取 → 启动报错。

## 4. 阶段 P1：信号与学习（L1–L7）

### L1 冻结自动学习，改为影子运行

- 冻结期间决策版本固定：在每条 decision 记录 `config_hash` 与各角色手册版本号，便于后续比较。
- `scoring.update_weights` 照常计算，但写入 `state/weights_shadow.json`，决策使用初始权重。
- `review.maybe_edit_playbooks` 只把建议写到 `playbooks/<角色>/proposals/`，不切换版本、不进入观察期。
- 日报“角色成绩单”同时显示实用权重与影子权重。

- 恢复条件见第 6 节 Q8，未得到用户答复前保持冻结。

### L2 打分方法修正

**现状**：固定 ±2% 判涨跌平，以 0.5 为基准；中性的基础命中率（约 16%–26%）远低于有方向观点（约 37%–42%），所有角色被系统性压权，常说中性的最惨，导致 |S| 变大、交易更激进。

**改为**：

0. **按观点自身条件打分**：评估窗口用该观点自己的 `horizon_days`（1–30），不再固定 5 天；条件入场观点（涨到/跌到）只有在有效期内价格触及入场价才开始计时，从触及点算收益；未触及记 `not_triggered`，不计命中也不计失误。这仍是“方向预测指标”，不等同交易贡献（交易贡献见第 5 点）。
1. 平区间改为波动率自适应：`band = 0.5 × ATR14% × sqrt(horizon_days)`，ATR 取观点当日值，写入 scores 记录。
2. 每条打分记录 `base_rate`：该币、该方向、近 365 天按同一 band 与 horizon 计算的无条件命中率。`skill = hit − base_rate`。
3. 影子权重公式改为收缩估计：`w = w0 × clip(exp(k × skill_shrunk), 0.5, 2.0)`，`skill_shrunk = Σskill / (n + n0)`，`n0` 新增配置默认 30，`k` 默认 4。同一天同一角色的三币观点在计算 n 时只算 1 个有效样本。
4. 置信度校准：日报增加每角色 Brier score 与三档置信（<0.4、0.4–0.7、>0.7）各自命中率。
5. **角色贡献拆成四个口径，分开记录**。现有 `pnl_attribution`（已平仓盈亏 × 角色方向 × 交易方向符号）会让一笔亏损多单给看空角色记正值，而该角色可能从未给出可执行的空单。它只是“与最终交易的方向一致性”，不是盈亏贡献，改名为 `direction_alignment`，日报注明含义。四个口径：
   - (a) 方向预测：第 0–2 点的 skill。
   - (b) 完整方案：该角色自己的入场/止损/目标/周期，按 R1/R2 规则纸面模拟的 R 倍数；方案不完整的记 `no_plan`。
   - (c) 实际交易净收益：只归属到最终执行的那笔交易，不拆给角色。
   - (d) 留一法：去掉该角色重算聚合，记录决策是否改变（开/不开、方向、方案组），以及改变后的纸面结果。这一项最接近“这个角色值不值得留”，与 B1 消融对照共用实现。
   四项都只展示，不进权重（受 L1 冻结约束）。

**验收**：构造一个永远中性、命中率恰好等于其 base_rate 的假角色 → skill≈0，影子权重 ≈ w0（不得因“中性”本身被压权）；构造永远看多的假角色，在单边上涨数据上 skill≈0（不得因顺势而被加权）。

### L3 共识：无效票剔除，主动中性保留

**现状**：`S = Σ w·dir·conf / Σ w`；解析失败、无发言都记作中性置信 0，仍占分母。

**改为**：

- 每个角色立场增加 `status`：`parsed` / `structured` / `extracted` / `neutral_active` / `failed` / `absent` / `data_missing`（L4）。
- `failed`、`absent`、`data_missing` **从分子和分母同时剔除**；主动给出中性的角色**保留在分母**。
- **明确不做**：不要把分母改成 `Σ w × conf`，也不要剔除主动中性票。否则一个低置信的孤立观点会被放大成满仓。
- 新增 `manager.min_valid_voters: 6`，有效票少于此数时不开新仓（`hold(有效票不足)`）。
- 日报角色观点表显示每个角色的 status。

**验收**：12 票中 1 票看多 conf=0.3，其余 11 票主动中性（等权）→ S≈0.025，不交易；同样情形其余 11 票全部 failed → 有效票不足，不交易。

### L4 输入缺失时取消对应角色的投票资格

- `flows.fetch` 失败项占比 ≥ 50% → flows 记 `data_missing`。
- FRED 不可用不取消 news 资格，只在日报标注。
- x_feed 缺失时发一次 webhook `x_feed_missing`（每日最多一次）。

### L5 交易经理收口

- 结构化输出新增 `risk_scale`（0–1，默认 1），作为 R1 中 `tm_risk_scale`，**只能缩小**。`size_pct`/`entry_size_pct` 保留字段兼容但不再参与计算（否决判定逻辑如依赖它们，改为依赖 `risk_scale ≤ 0`）。
- `leverage` 字段只作为上限（只降不升）。
- **明确不做**：不要让交易经理或任何 LLM 直接决定仓位、杠杆、止损价。

## 5. 阶段 P2：运维、安全、研究、对照组

### O1 进程守护与定时任务

交易台运行在 Grok Bot 宿主上。没有 cron 本身不是缺陷，要保证的是：触发确定、失败可见、重复触发不重复交易、宿主重建后可恢复。具体方案必须适配 Grok Bot 宿主（依据 V5、V12），不预设 systemd。

1. **调度确定化**：每日入口统一为固定命令 `bash run_daily.sh`，脚本内部完成单实例锁、当日完成标记 `state/daily_done/<日期>`、时间窗口检查（只允许 07:55–12:00 首次执行）。例行任务提示词改为“只执行这条命令并回报返回码”，**是否执行、何时执行不交给模型判断**；模型只负责流程内部的分析。x_feed 采集作为独立固定步骤，在 run_daily 之前执行，失败不阻塞 run_daily（按 L4 处理）。
2. **重复触发保护**：已完成则退出 0；正在运行则退出并记 `daily_duplicate_trigger`。验收：连续触发两次，只有一次进入交易流程。
3. **常驻进程守护**：按 V5/V12 实测选择宿主支持的方式（systemd --user、supervisord，或宿主平台自带的重启策略）。都不可用 → **停下询问用户**，不要用 `@reboot` 等方式绕过。由守护工具负责重启后，`run_demo_ws.sh` 内部循环与 `healthcheck.py` 的重启逻辑要避免冲突，在报告中写明最终方案。
4. **宿主重建恢复**：若 V12 显示 `/workspace` 可能不保留，`state/`（不含 `secrets.env`）每日打包备份到宿主外（目的地见 Q12）；新增 `scripts/bootstrap.sh`：检查 venv、拉起常驻进程、跑一次对账（R11.3）与止损覆盖检查（R11.4），并发 webhook `bootstrap_done`。
5. **健康检查升级为链路检查**：除进程存在与新鲜度外，每轮加：模拟盘私有接口可达（account/config）、每个持仓止损覆盖完整（R11.4）、demo_ws 最近 N 分钟收到过消息或 pong、本地登记与交易所对账无差异。任一失败发 `chain_unhealthy`。“进程存在”不能再被报告为“正常”。

### O2 告警补齐（走现有 `TA_NOTIFY_WEBHOOK_URL`）

|---|---|---|
| `daily_missing` | 北京时间 09:30 仍无 `reports/<今日>.md` | 每日一次 |
| `daily_failed` | `run_daily` 返回码非 0 | 每次 |
| `x_feed_missing` | L4 | 每日一次 |
| `healthcheck_stale` | `healthcheck.log` 超过 30 分钟未更新（由 demo_watch 顺带检查） | 每小时一次 |
